# Сейв и ProfileStore

## Всё сохраняемое — разделы сервисов + атрибуты, папок `PlayerData` нет

Папки `Value`-инстансов для простых полей рядом с разделами сервисов для сложных — два механизма для одного, и папки реплицируют клиенту то, что ему не нужно (`FirstJoin`, `TotalPlaytime`). Поэтому каждое поле принадлежит сервису-владельцу раздела, нужное клиенту сервис публикует атрибутом игрока, служебная статистика — раздел `Stats` самого `SavesLoader`.

Цена: схема сейва разнесена по сервисам (сводка — [saves](../docs/systems/saves.md#разделы)); значения по умолчанию задаёт владелец в `LoadSave`, шаблона профиля нет. Клиент атрибут может поменять только у себя — на сервер это не уходит, как и с папками. Сейвы старой схемы (`Currencies.Cash`, `TotalStats`) новыми разделами не читаются: на живой игре со старым шаблоном нужен мигратор.

## Сложные разделы принадлежат сервисам

Загрузчик, знающий каждую структуру игры, — правка одного файла на каждый раздел и кэш, который некому валидировать. Сервис сам знает, что должно лежать в его разделе.

**Владелец находится по соглашению** (`SaveSection` + методы), а не списком в конфиге: расхождение списка с кодом молчаливо, раздел просто перестал бы грузиться.

**Данные отдаёт неразрушающий `GetSave`**, а `UnloadSave` только отпускает кэш. Автосейв пишет много раз за сессию, и разрушающий метод перед каждой записью дал бы пустоту на второй записи. `nil` из `GetSave` — «сейв не читался»: записать пустоту вместо непрочитанного значит стереть прогресс.

## ProfileStore, а не свой загрузчик

У записи один раз на выходе через `SetAsync` две цены: падение сервера теряет сессию целиком (в том числе уже помеченную покупку), а второй плейс с общим `DataStore` затирает покупки первого, причём молча. ProfileStore закрывает обе: лок ключа и автосейв.

**Не свой лок:** это полторы сотни строк в каждом плейсе, без реакции через `MessagingService` и `IsCriticalState`. Взят **ProfileStore**, а не `ProfileService`: второй у того же автора legacy с 2024 года.

## Синк, а не запись прямо в `profile.Data`

Живой кэш — кэши владельцев разделов; `syncToProfile` переливает их на `Profile.OnSave`. Запись в `profile.Data` из каждого сервиса размазала бы знание о ProfileStore по серверу. Цена шва: прогресс обязан быть виден через `GetSave`, а `syncToProfile` не йилдит.

## `IsLoaded` ставится и при провале

Атрибут значит «загрузка закончилась». Без него клиент висел бы на старте без строки в консоли. Дальше решает `KickOnLoadFail`: в игровом плейсе кик лучше игры на дефолтах, затирающих прогресс. Флаг «игрок загружен» гвардом записи быть не может — его снимает чужой обработчик того же события; гвард — `profile:IsActive()`.

## `/wipe` для разработчиков: стереть всё и кикнуть

Команда чата `/wipe` (`TextChatCommand` на сервере, `SavesConfig.WipeCommandAlias`) для Id из `DevelopersConfig` стирает свой сейв целиком, включая `Stats`, и кикает с `SavesConfig.WipeMessage`; на заходе все разделы грузятся как у нового игрока (`LoadSave(player, nil)`). Делает `SavesLoader:WipeSave`: флаг сброса, очистка `profile.Data`, `EndSession`, кик. Флаг гасит `syncToProfile` — иначе кэши сервисов при выходе и в последней записи сессии вернули бы стёртое — и подмену кика текстом «сохранение открыто в другой игре».

Почему кик и перезаход, а не сброс на месте: сброс на месте требует пути перезагрузки каждого сервиса на ходу. Список — ключами `DevelopersConfig`: эти же аккаунты получают бесплатные dev-покупки вне Studio (`Monetization:PromptProduct`/`PromptPass`). В шаблоне список пуст — UserId заводит каждый проект.

Цена: Studio пишет в настоящий `DataStore` — `/wipe` в Studio стирает реальный сейв аккаунта; проверять сам сброс — с `SavesConfig.UseEmptySave = true`.

## `Connect` раньше обхода уже вошедших

`onPlayerAdded` йилдит трижды (политика, лок, геймпассы). При обратном порядке игрок, вошедший во время обхода, не получал `IsLoaded`. Лок может ждать секундами, поэтому у `StartSessionAsync` обязателен `Cancel`.
